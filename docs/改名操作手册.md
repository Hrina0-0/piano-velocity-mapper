| 项目 | 状态 | 说明 |
|---|---|---|
| 提交邮箱换成带数字 ID 格式 | ✅ 已完成 | `275496685+lanminhua666-dotcom@users.noreply.github.com` |
| 候选名可用性实测 | ✅ 已完成 | `Hrina0-0` 返回 404 = 未被占用 |
| 候选名格式合法性 | ✅ 已完成 | 只含字母数字与单个连字符，长度 8 ≤ 39 |
| 改名后收尾脚本 | ✅ 已就绪 | `dev/after_rename.ps1` |

**为什么提交邮箱要换成带 ID 的格式？**

GitHub 有两代 noreply 邮箱格式：

- 旧格式 `用户名@users.noreply.github.com` —— 改名后**会失去归属**，提交不再计入贡献图
- 新格式 `数字ID+用户名@users.noreply.github.com` —— 数字 ID 是账号的稳定标识，**改名后依然关联**

你仓库原有 14 个提交用的正是旧格式。改名前把仓库级 `user.email` 切成带 ID 格式，
只能保证**今后**的新提交不再掉署名；已经存在的 14 个旧提交在改名瞬间仍然失联，
需要在改名后靠重写历史补救（实测过程见第七节）。

**最稳的做法：以后任何一次改名之前，都先把 `user.email` 切成带数字 ID 的格式。**

## 七、旧提交署名：实测失联 → 已修复

### 7.1 问题

改名后逐个核对 16 个提交的 GitHub 账号关联（`GET /repos/{owner}/{repo}/commits`）：

| 提交 | 作者邮箱 | `author.login` |
|---|---|---|
| `2868d2d`（改名前用带 ID 格式提交） | `275496685+lanminhua666-dotcom@users.noreply.github.com` | ✅ `Hrina0-0` |
| 其余 14 个（改名前用旧格式提交） | `lanminhua666-dotcom@users.noreply.github.com` | ❌ `null` |

**结论**：官方文档的说法得到实测确认 ——
旧式 `用户名@users.noreply.github.com` 在账号改名后**立即失去归属**；
带数字 ID 的 `数字ID+用户名@users.noreply.github.com` **不受改名影响**，
因为数字 ID `275496685` 是账号的稳定标识。

影响：仓库页面上这 14 个提交仍显示作者姓名 `Hrina`，但头像与主页链接缺失，
不计入账号贡献图。

### 7.2 修复方式

把 14 个旧提交的作者邮箱重写成带 ID 格式，再 force push：

```powershell
cd D:\Codex-work\repiano_pkg

# 先备份（bundle 含全部分支与标签，校验输出 "records a complete history"）
git bundle create D:\Codex-work\repiano_pkg_backup.bundle --all
git bundle verify D:\Codex-work\repiano_pkg_backup.bundle

# 重写作者与提交者邮箱（filter-branch 会自动在 refs/original/ 留一份原历史兜底）
$env:FILTER_BRANCH_SQUELCH_WARNING = '1'
git filter-branch -f --env-filter 'if [ "$GIT_AUTHOR_EMAIL" = "lanminhua666-dotcom@users.noreply.github.com" ]; then export GIT_AUTHOR_EMAIL="275496685+Hrina0-0@users.noreply.github.com"; fi; if [ "$GIT_COMMITTER_EMAIL" = "lanminhua666-dotcom@users.noreply.github.com" ]; then export GIT_COMMITTER_EMAIL="275496685+Hrina0-0@users.noreply.github.com"; fi' --tag-name-filter cat -- --all

# 强制推送分支与标签
git push --force origin main
git push --force origin v1.3.0
```

> `filter-branch` 只改提交元数据，**不碰文件内容**。
> 重写前后 HEAD 的 tree hash 完全一致（`9292629452296c69b929dafd74bec876fc9bd07f`），
> 工作区 `git status` 干净，可确认内容零改动。

## 八、Release 附件：本地包与线上包字节不同是正常的

排查时发现 `release\PianoVelocityMapper-v1.3.0.zip` 与线上附件的 SHA256 不同，
原因是**两边不是同一台机器构建的**：

| | 本地 `release/` 包 | 线上 Release 附件 |
|---|---|---|
| 构建者 | 本机 `.venv` + `make_release.ps1` | **GitHub Actions**（`.github/workflows/build-windows.yml`，打 tag 触发） |
| 环境 | 本机 Python / pyinstaller | `windows-latest` + Python 3.13 |
| `PianoVelocityMapper.exe` | 19 060 407 字节 | 19 259 578 字节 |
| `创建桌面快捷方式.cmd` | 506 字节（LF） | 520 字节（**CRLF**） |
| `make_shortcut.ps1` | 926 字节（LF） | 952 字节（**CRLF**） |

两个包**功能等价**，字节不同的两个原因：

1. **行尾**：`.gitattributes` 规定 `*.cmd` / `*.ps1` 用 CRLF（cmd.exe 在 CRLF 下最稳），
   CI checkout 出来的是 CRLF 版（506→520、926→952，正好每个换行多 1 字节）；
   而本地工作区这两个文件当前是 LF（由编辑器/工具写入导致）。
2. **exe**：PyInstaller 在不同 Python 版本与依赖集下产物大小不同。

**结论：线上附件才是符合 `.gitattributes` 规范的正确产物，不要用本地包去覆盖它。**
`release/` 目录被 `.gitignore` 排除，本来就只是本地产物。
